# Tiny Nations C# 与框架开发规范

本文是项目自有 C# 代码的权威规范，适用于 `Assets/Scripts/BorFramework` 与
`Assets/Scripts/GameLogic`。框架结构与使用方式另见 [框架总结](FrameworkOverview.md)，文件放置规则另见
[目录规范](DirectoryStandards.md)。

## 1. 核心原则

按以下顺序做取舍：

1. **正确且可释放**：进入、运行、退出、再次进入后状态仍然正确，订阅与资源都有明确回收点。
2. **直接且可读**：优先早返回、清楚命名和短调用链，不用抽象掩盖简单逻辑。
3. **边界清晰**：框架只提供跨玩法复用的稳定能力，具体玩法留在 `GameLogic`。
4. **依赖可见**：必需依赖通过构造函数或 Inspector 显式提供，不在深层代码中临时查找全局对象。
5. **按需求演进**：没有真实使用场景时，不预建通用容器、反射注册、复杂 Result、对象池或兼容层。

代码优雅不等于代码最短。这里的“优雅”指职责单一、所有权明确、失败路径可见、离开功能时能完整清理。

## 2. 框架边界与依赖方向

依赖只允许沿下列方向发生：

```text
GameBoot（应用组合根） ─────> GameLogic
          │                   业务功能
          └───────────────> BorFramework ─────> Unity / 已选定的第三方库
                             通用运行时能力
```

- `BorFramework` 不引用 `GameLogic`，也不包含具体角色、关卡、数值或界面业务。
- 普通 `GameLogic` 代码通过 `I...Module` 使用框架，不依赖模块实现类。
- 模块之间通过最小接口和构造函数依赖，不直接从任意位置调用 `GameHub` 获取彼此。
- `GameBoot` 位于应用层，是唯一组合根：创建框架实现、注入依赖、注册模块，并加入全程业务 System。
- `BorFramework` 只提供可组装的运行时能力，不通过静态注册表或反射发现具体业务类型。
- 新能力只有在至少两个独立业务场景需要相同生命周期与语义时，才考虑下沉到框架。

新增代码前先判断：

| 问题 | 是 | 否 |
| --- | --- | --- |
| 它是否是跨玩法、跨场景的基础能力？ | 考虑放入 `BorFramework` | 放入对应 `GameLogic/<Feature>` |
| 它是否需要统一启动、停止和释放？ | 考虑实现 Module 或 GameSystem | 使用普通类或 MonoBehaviour |
| 它是否只服务一个界面或角色？ | 留在该功能目录 | 再判断是否属于共享业务 |

## 3. 类型与文件

- 一个主要类型对应一个 `.cs` 文件，文件名与类型名一致。
- 只服务宿主类型、很短且不会被单独复用的 `private` 嵌套类型可以留在同一文件。
- 类型默认使用最小可见性；无需继承的具体类型使用 `sealed`。
- 接口以 `I` 开头；枚举类型以 `E` 开头；事件数据使用 `...Event`；模块接口使用 `I...Module`。
- 不使用拼音、无意义缩写、`Manager`/`Helper`/`Utils` 等不能表达职责的宽泛名称。
- Namespace 与业务边界一致：框架使用 `BorFramework`，业务使用 `GameLogic.<Feature>`。
- 不让 Namespace 跟随每一层物理目录无限变长；目录用于导航，Namespace 用于表达代码边界。

## 4. 命名与类内顺序

- 类型、方法、属性、事件、常量、枚举值使用 `PascalCase`。
- 参数和局部变量使用 `camelCase`。
- 私有字段使用 `_camelCase`；Inspector 数据优先使用 `private [SerializeField]` 字段。
- 布尔值使用能直接读成判断的问题式名称，如 `IsReady`、`HasOwner`、`CanLoad`。
- 方法用动词表达动作；`Try...` 必须以 `bool` 表示是否成功，并通过 `out` 返回结果。
- 时间、距离、索引等容易误解的值在名称或注释中说明单位和边界。

类内成员按以下顺序组织：

1. 常量、静态字段；
2. 序列化字段、只读依赖、其他实例字段；
3. 属性、事件；
4. 构造函数；
5. Unity 或框架生命周期方法；
6. public、protected、private 方法；
7. 必要的嵌套类型。

每行尽量不超过 120 字符。一个变量一行，不做与当前需求无关的排序或格式化。

## 5. 控制流与失败处理

- 优先用空值检查、状态检查和早返回，避免深层嵌套。
- 项目自有代码不添加 `try`、`catch`、`finally`。
- 正常业务失败不使用 `throw`，使用 `bool`、`null`、`Try` 方法或聚焦的状态枚举。
- 不静默吞掉会导致功能不可用的失败；在拥有足够上下文的边界记录一次可定位日志。
- 不在每帧失败路径持续刷日志。配置错误可在初始化或首次发现时记录。
- `null` 或 `false` 的语义必须能从方法名、XML 文档或接口约定中判断。

日志至少包含“发生了什么”和可定位的关键上下文，例如资源 address、场景名或类型名；不要只写“失败”。

## 6. 生命周期与所有权

框架对象必须遵循成对生命周期：

```text
Init  ->  Start  ->  Stop  ->  Dispose
一次      可运行     停止运行    永久释放
```

- `Init` 建立内部状态，不开始依赖帧循环的行为。
- `Start` 订阅帧回调、事件或开始运行；重复调用不得重复订阅。
- `Stop` 取消 `Start` 建立的运行关系；允许对象之后再次 `Start`。
- `Dispose` 先停止，再按创建的逆序释放持有对象并清空集合。
- 创建者默认是所有者；所有权转移必须由 API 名称、返回类型或文档明确表达。
- 事件订阅、帧回调、资源租约、异步请求上下文必须有对应的取消、关闭或释放位置。
- `IAssetLease<T>` 表示资源所有权。接收成功后由接收方负责 `Dispose()`；转移失败时由原持有者释放。
- 集合遍历期间不直接修改同一集合；使用延迟队列、快照或明确的更新后提交阶段。

## 7. Module、GameSystem、Entity 与 MonoBehaviour

### Module

Module 是跨业务的全局服务。每个 Module：

- 提供小而稳定的 `I...Module` 接口；
- 实现一个明确职责，不互相循环依赖；
- 由 `GameBoot` 构造和注册；
- 注册、启动按依赖顺序，停止、释放按逆序；
- 不把具体玩法 API 塞进通用模块。

### GameSystem

GameSystem 管理一项业务功能的生命周期，例如战斗流程或关卡规则。它适合纯 C# 编排，不用于替代所有普通类。
System 必须能从 `IGameSystemModule` 移除，并在移除时完整执行 `Stop` 与 `Dispose`。
`AddSystem` 返回 `true` 后才转移所有权；注册失败时由调用方处理候选对象。场景级 System 应在退出时调用 `RemoveSystem<T>`，不能只丢弃引用。

### Entity / Logic / Component

- `Entity` 负责组合能力与所有权，不承担所有业务细节；子类直接保存 Component 并注入 Logic，不重建按类型查询的容器。`AddLogic` 仅用于首次启动前装配。
- `Logic` 实现可更新行为。公开 `OnUpdate / Stop / Dispose` 由基类控制；子类覆写受保护的 `OnStart / OnTick / OnStop / OnDispose`，临时运行关系在 OnStop 解除，永久资源在 OnDispose 释放。
- `Component` 保存数据、Unity 引用及维护局部状态不变量的方法；帧调度、跨组件伤害结算和事件发布放在 Logic，不在无需求时演变为通用 ECS。
- `IEntityModule.AddEntity` 成功后接收实体所有权。更新中请求移除会延迟释放，依赖实体结束的 GameObject 回收和租约释放必须放在 `RemoveEntity(entity, onRemoved)` 完成回调中。
- 同一 Entity 的 Logic 按 Phase 排序，同 Phase 保留装配顺序；不要假设所有 Entity 已完成同一阶段才进入下一阶段。
- 只有需要统一帧调度和生命周期的场景对象才进入 Entity；简单场景表现可以保留为 MonoBehaviour。

### MonoBehaviour

- MonoBehaviour 主要承担 Unity 边界：序列化引用、Unity 消息、GameObject/Component 操作。
- 可测试的业务规则尽量放入普通 C# 类型。
- 不在 `Update` 中反复查找组件、模块或资源；在初始化阶段缓存必需引用。

## 8. 异步、资源与场景

- 异步方法使用 `Async` 后缀；除 Unity 入口桥接外返回 `UniTask` 或 `UniTask<T>`，避免 `async void`。
- `.Forget()` 只用于明确的顶层入口，内部流程应继续返回任务和成功状态。
- `await` 后重新检查宿主是否仍有效、请求是否仍是最新版本、导航或场景上下文是否仍成立。
- UI 的 Screen/Window 必须通过模块导航规则打开；同类型在栈中时拒绝重复压栈，调用方需要处理异步返回 `null`。被后续页面隐藏的 Screen 仍属于打开生命周期，`IsOpen` 不等于当前可见。
- 同一个 `UniTask` 不重复 await；需要共享结果时使用框架允许的保留方式或等待显式状态。
- 资源通过 address 与 `IResourceModule` 加载，不在业务层直接绑定 YooAsset 实现。
- 场景切换以 `ISceneModule` 的返回结果为准；不要把“请求发出”当成“场景可用”。
- `Resources` 只保留 Unity 启动前确实无法通过框架加载的最小资产。

## 9. API、注释与文档

- 公开 API 应让调用方从名称和类型看懂所有权、失败方式与生命周期。
- 非显而易见的 public API 使用 XML 文档说明参数、返回值、约束和所有权。
- 注释解释原因、约束、单位、阶段或所有权，不复述代码。
- 不保留注释掉的旧代码；TODO 必须说明完成条件，不能只是模糊愿望。
- 公开接口、模块注册顺序、资源所有权或目录约定变化时，同步更新 `Assets/Doc`。

## 10. 第三方、生成代码与改动范围

- 不修改 Unity Packages、YooAsset、UniTask、Odin、DOTween 等第三方内部实现来迎合本规范。
- 不手动修改 Input System 等工具生成的代码；从源资产或生成配置解决问题。
- 不因一次需求顺手重构无关文件，不批量格式化现有代码。
- 修改或移动 Unity 资产时保留 `.meta` 与 GUID，并检查场景、Prefab、YooAsset collector 和 address 引用。

## 11. 完成标准

一次框架或业务代码修改至少确认：

- 受影响代码能够在当前 Unity 版本下编译；
- 进入、退出、再次进入的生命周期能够闭环；
- 订阅、帧回调、实例和资源租约没有遗留；
- 失败路径有安全返回值，必要时有一次可定位日志；
- 新文件位置符合目录规范，依赖方向没有反转；
- 没有修改第三方、生成代码或无关用户改动；
- 行为相关修改使用当前运行结果验收，历史日志或单纯文件存在不算完成。
